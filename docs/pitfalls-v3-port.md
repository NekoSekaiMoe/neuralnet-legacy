## 坑 1：GEMM 微内核越界读 —— `sNaN × 0 = NaN` 污染整个累加器

**症状**：`nn::Muon` 在最简单的 rank-1 用例上输出 `-nan`。逐行复算
Newton-Schulz 的标量版本完全正常；单独抽出 `gemm_microkernel_` 写纯 C++
测试程序（4×64 乘 64×8 的 ones）也完全正常。问题只出现在走 `Matrix`
完整分块路径时。

**定位过程**：

1. 用 ones 矩阵做 canary：`64×64×64` 单块就错（min=0，max=512）。
   但 `3×2 × 2×3` 的小矩阵**全对** —— 这个"通过"是假阴性，见坑 2。
2. 微内核单测通过、Matrix 路径失败 → 缺陷不在内核算术，在调用点的
   参数或越界行为。
3. 打印 Muon 实际值与标量递推值对比，确认 NaN 来自矩阵乘法内部。

**根因**：微内核最初把 kk 循环写成走满编译期常量 `BLOCK_SIZE`（64），
思路是"B 面板零填充，越界部分乘 0 不影响结果"。但 **A 行块直接指向
原矩阵**（`ap = data_.data() + i*K + k_start`），当 K 不是 64 的倍数、
或矩阵本身只有 4 列（Muon 的 4×4 参数）时，`ap[ii*a_stride + kk]` 读到
k 块之外的堆内存 —— 这是 UB。更糟的是：垃圾字节按 double 解读可能是
**sNaN（signaling NaN）**，而 IEEE 754 里 **`sNaN × 0.0 = NaN`，不是 0**。
一个 NaN 进入 `acc[4][8]` 寄存器块，整个 4×8 输出瓦片全灭。

**修复**（`matrix.h:76`）：给微内核增加 `k_len` 参数，kk 循环以 k_len 为界
（调用点传 `k_len, std::min(MK_RB, j_len - j0)`）。B 面板保留零填充
（向量 load 仍安全），A 侧彻底不越界。

**为什么上游没踩**：上游 `algebra_matrix.hpp` 有一个独立的
`dot_span_`（定长点积，尾块专用）—— 它只在 k 块完整时调用微内核，
尾部 K 块走标量路径。移植时只搬了微内核、没搬尾块分流，就踩了坑。

**教训**：
- **"只 padding 一个操作数就够了"是错的**。另一操作数的越界读是 UB，
  且 IEEE 754 的 NaN 语义（sNaN 参与任何运算 → NaN）会穿透"乘 0 归零"的假设。
- 复刻别人代码时，看不懂的"多余"分支（如 dot_span_）往往是踩过坑的产物，
  删掉之前先想清楚它防什么。

## 坑 2：微内核写回漏 j0 偏移 —— 8 个列瓦片叠写到同一组列

**症状**：128×128 的 ones 矩阵相乘，期望全 128，实测 min=0、max=1024。

**定位过程（因子取证法）**：

1. 分块二分：`64×64×64` 单块就错 → 与多块边界无关。
2. 观察异常值的"指纹"：**1024 = 8 × 128**，而 8 正好是 `MK_RB`
   （微内核列宽）。未写到的列是 0。这几乎直接指认"j0 循环的 8 个瓦片
   全部落到了同一处"。
3. 检查调用点：`bp = b_pack.data() + j0`（B 侧带了 j0），但
   `rp = result.data_.data() + i*N + j_start`（**输出侧没带 j0**）。
   每个列瓦片都把贡献加到 j_start 起的 8 列上：8 倍累加 + 其余列恒 0。

**修复**（`matrix.h:316`、`matrix.h:474`）：写回指针补上 j0 ——
`result.data_.data() + i*N + j_start + j0`（`operator*` 与 `matmul_TN` 两处）。

**假阴性陷阱**：最初 3×2 的小矩阵全对，让人误以为内核正确。实际上
`i_len(3) < MK_NI(4)`，一行都没走微内核，全落在标量回退路径 ——
**新路径根本没被执行**。后续补的 `gemm_microkernel_odd_shapes` 测试特意
选了 ≥4 行的尺寸（67×53、257×65 等）保证微内核必走。

**教训**：
- ones 矩阵 + min/max 指纹是最快的分块数学分 bug 手段；异常值里的
  倍数因子（8×）往往直接就是肇事循环的名字。
- "小尺寸用例通过"≠"覆盖了新代码"。测试选尺寸时要确认**目标分支
  真的被执行**（行数 ≥ MK_NI、列数跨 j0 瓦片、K 跨块）。

## 坑 3：线程池 Use-After-Free —— 裸指针逃出锁的作用域

**症状**：`threadpool_parallel_for` 在 ctest 下偶发 SEGFAULT（单跑常过）。

**根因（竞态时间线）**：

```
worker                                dispatcher (parallel_for 调用方)
──────                                ──────────────────────────────
lock(mtx_)
job = queue_.front()      ← 裸指针
unlock(mtx_)
                                      （最后一个块 remaining → 0）
                                      lock(mtx_) → pop front → unlock
                                      dispatch_ 返回 → Job（栈上对象）析构
读 job->remaining        ← UAF：对象已销毁
```

Job 原本存活在 `dispatch_` 调用方的栈上；worker 拿到裸指针后释放了锁，
此后到解引用之间的任何时刻，任务都可能被完成、弹出、析构。
worker 的"已完成头部清理"分支（锁外读 `job->remaining` 再回锁内二次确认）
是同一个错误的两份拷贝。

**修复**（`threadpool.h:54,127`）：

1. 队列与局部变量全部改持 `std::shared_ptr<Job>` —— worker 在锁内拷贝
   shared_ptr，之后无论队列怎么弹、调用方怎么返回，对象保活；
2. "是否已完成 / 是否要清理"的判断全部收进锁内（front 的弹出只可能
   由持锁者执行，判断期间不会被抢走）；
3. 顺带修正：`reduce_chunks_` 的 partials 也改为 `shared_ptr<vector<T>>`，
   与 Job 生命周期解耦。

验证：UBSAN 干净 + 30 次压测循环全过（本机 ASAN 不可用，见附录 B）。

**教训**：
- **指针一旦逃出锁的保护范围，就必须带走所有权**（shared_ptr / 引用计数
  / epoch 回收任选其一）。"我刚才在锁里检查过"不算数 —— 锁外的世界会变。
- 低概率复现的崩溃（单跑过、CI 偶挂）优先怀疑生命周期而非逻辑；
  写并发原语时默认问一句："这个指针比谁活得久？"

## 坑 4：KeyValueRecord 未知类型"跳过"了值、没跳过字段

**症状**：构造一条 type=99（未知类型）+ 一条正常 UInt 的字节流做
向前兼容测试，`!rec.has("x")` 断言失败 —— 未知字段仍然进了库。

**根因**：`parse()` 的 switch 里 default 分支只做了
`bytes.remove_prefix(value_len)`（值层面正确跳过、游标不乱），但
switch 结束后有一段**共享尾部代码** `fields_.push_back(std::move(f))`，
default 也走到了它。而 `has()` 只按 key 查找不看类型，于是"跳过"名存实亡。

**修复**（`keyvalue_record.h:184`）：`bool unknown` 标志 + `if (!unknown)
push`。语义明确为：未知类型的字段**整个不入库**，后续字段照常解析。

**教训**：
- "跳过"类分支必须能被测试观测到（`has()`/`get()` 都要验），否则
  它只是把游标推对了，坏数据照样进结果。
- switch 之后共享的收尾代码是伪装成 break 的 fall-through：任何"部分
  处理后提前退出"的分支，都要显式地和入库决策解耦。

## 附录 A：本批次用过的定位手法小结

| 手法 | 用在哪 | 说明 |
|------|--------|------|
| ones 矩阵 canary | 坑 1、2 | 全 1 输入让分块数学的期望值唯一（=K），一眼看出错位/漏写/重复累加 |
| 因子取证 | 坑 2 | 异常值 1024 = 8×128，倍数 8 直接指向 MK_RB 瓦片循环 |
| 分块二分 | 坑 1、2 | 64³ 单块 vs 多块，先排除边界再查内核 |
| 最小复现剥离 | 坑 1 | 把微内核抽成独立程序，把"内核错"和"调用错"分开 |
| 标量影子实现 | 坑 1（Muon 测试） | rank-1 情况下 NS 迭代退化为一维递推，可逐位精确对照 |
| 压测循环 + UBSAN | 坑 3 | 低概率竞态用次数换概率，UBSAN 兜住解引用类 UB |

## 附录 B：本机环境限制（调试时必读）

- **ASAN 在本机（aarch64，39 位虚拟地址）完全不可用**：shadow memory
  映射不进去，连未改动的 `relu` 测试都会报
  `heap size 40000002000 exceeds max user virtual address`。这不是代码
  问题的信号 —— 别被它带偏。
- 替代手段：UBSAN（无 shadow，可用）+ 竞态类 bug 用压测循环放大。
- aarch64 NEON 是 128-bit：`MK_RB = 8`（双精度）在 NEON 上由编译器拆成
  两条向量指令，微内核仍有效（实测 3.5~4×），但绝对上限低于 AVX2 机器。
